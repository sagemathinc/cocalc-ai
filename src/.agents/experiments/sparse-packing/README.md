# Sparse Packing Feasibility Experiment

Date: 2026-09-05. This is a disposable local experiment, not a production encoder
or approval to change backup representation.

## Result

Packing sparse files before Rustic and expanding them afterward works for the
tested Linux/Btrfs fixtures. It avoids both logical-size restore expansion and
Rustic processing the original holes. Small edits preserve useful chunk-level
deduplication. However, naively replacing every sparse file with a newly generated
archive on every backup loses Rustic's unchanged-file fast path, even when the
archives are byte-identical and add no new file blobs.

Reusing a persistent packed staging tree avoided repacking and let Rustic reuse
all unchanged file content. Copying that tree to a new directory with reflinks
lost the metadata fast path again. This is **not** a test of Btrfs subvolume
snapshots: do not infer that snapshots themselves change file identity in the
same way as `cp`. The actual per-backup snapshot/cache integration remains open.

## Reproduce

Requirements: Node.js, GCC, GNU tar, GNU cp, findmnt, and an explicitly supplied
Rustic executable. `/tmp` must be Btrfs. The harness uses generated files and
fresh local repositories with isolated HOME/config/cache/credentials. It does not
call CoCalc APIs, use production repositories, or inherit repository credentials.

```sh
node src/.agents/experiments/sparse-packing/probe.cjs \
  /absolute/path/to/rustic /tmp/sparse-packing-report.json
```

The command compiles `extent-check.c` inside its disposable directory and removes
fixtures, binaries, and repositories afterward. The optional JSON report remains
at the requested path; stdout also records results. Each child command has a
60-second timeout. Input data and all filenames are generated by this harness;
its tar extraction is not intended for hostile archives.

Tested with GNU tar 1.35 and both installed Rustic 0.11.1 and official Rustic
0.11.4. Each version passed 11 backup/restore cases and `check --read-data` on both
repositories. Each case restores and verifies all four sparse files and twelve
ordinary 1 MiB files, not just the changed file. Each experiment uses default
Rabin chunking and random incompressible islands, so exact chunk/upload sizes and
timings vary between runs.

## Sparse Round Trips

Each sparse file is packed separately, without compression, using:

```sh
tar --create --file PACKED.tar --format=gnu \
  --sparse --hole-detection=seek --directory SOURCE -- FILE
```

Rustic backs up and restores the resulting dense tar files without any sparse
restore option. GNU tar then expands each into fresh staging. This worked with
0.11.1 as well as 0.11.4; it does not depend on Rustic PR 530.

| Fixture                    | Logical size | Source allocated | Packed tar size  | Decoded allocated |
| -------------------------- | ------------ | ---------------- | ---------------- | ----------------- |
| Two data islands           | 100 GiB      | 1 MiB            | 1,054,720 bytes  | 1 MiB             |
| Two larger data islands    | 10 GiB       | 64 MiB           | 67,112,960 bytes | 64 MiB            |
| 256 separated data islands | 256 MiB      | 16 MiB           | 16,793,600 bytes | 16 MiB            |
| Entirely holes             | 1 TiB        | 0                | 10,240 bytes     | 0                 |

Measurements follow `fsync`. The checker compares logical lengths, then every
byte in the union of source and destination data extents using `SEEK_DATA` and
`SEEK_HOLE`; ranges reported as holes by both need no reads. This verifies the
complete logical contents without reading a terabyte of zeros. A negative control
writes nonzero data into a source hole in a copy and confirms detection. Comparison
work is capped to catch accidental dense expansion without starting a huge scan.

## Incremental Behavior

Representative 0.11.4 results, with 81 MiB of real sparse-file data plus 12 MiB of
ordinary files. Upload columns mean newly stored file blobs in the local Rustic
repository, not measured network traffic. Small snapshot/tree metadata is separate.

| Case                                       | Sparse files encoded | Files reused by Rustic | New packed file blobs | Encode + backup wall time |
| ------------------------------------------ | -------------------- | ---------------------- | --------------------- | ------------------------- |
| Repack all, initial                        | 4                    | 0 / 16                 | About 93 MiB          | 2.02 s                    |
| Repack all, no source edits                | 4                    | 12 / 16                | 0                     | 1.42 s                    |
| Reuse artifacts, no source edits           | 0                    | 16 / 16                | 0                     | 0.34 s                    |
| Edit 4 KiB in one ordinary file            | 0                    | 15 / 16                | 1.00 MiB              | 0.38 s                    |
| Edit 4 KiB in the 16 MiB payload           | 1                    | 15 / 16                | 3.74 MiB              | 0.53 s                    |
| Edit 4 KiB in the 64 MiB payload           | 1                    | 15 / 16                | 3.24 MiB              | 1.20 s                    |
| Edit 4 KiB, restore original mtime         | 1                    | 15 / 16                | 0.87 MiB              | 0.40 s                    |
| Add a 4 KiB extent inside a hole           | 1                    | 15 / 16                | 1.00 MiB              | 0.40 s                    |
| Reflink-copy the whole packed staging tree | 0                    | 0 / 16                 | 0                     | 0.83 s                    |
| Repeat without changing that copied tree   | 0                    | 16 / 16                | 0                     | 0.34 s                    |

The warm unchanged snapshot grew the repository by 602 bytes, with no new file
or tree blobs. The repack-everything version added no file blobs either, but tar
processed all 81 MiB of mapped data and Rustic classified all four packed files
as changed. The fresh-directory reflink case classified all sixteen as changed.
Source inspection of Rustic's parent/file archiver confirms these changed files
take the read/chunk/hash path; `total_bytes_processed` alone does not measure
physical reads because it also counts reused files. No syscall read tracing or
cold-cache I/O benchmark was performed.

The 0.11.1 repeat also reused all sixteen unchanged files, added no file blobs,
and grew the repository by only 593 bytes. Its 4 KiB edit in the 64 MiB payload
added about 4.10 MiB of packed file blobs, not the full payload.

The prototype cache compares source metadata including nanosecond ctime, mtime,
size, inode, and ownership. Resetting mtime after changing contents was detected
and the new bytes restored correctly. This does not establish a production-safe
identity scheme across source snapshots, inode reuse, migration, or concurrent
writers; those need explicit source-version handling. Neither global
`--ignore-ctime` nor trusting just size and mtime is a proposed shortcut.

Changes inside a sparse file still require re-encoding its real data and Rustic
rehashing the packed payload. For the 64 MiB payload, only a few MiB were newly
stored, but all 64 MiB were presented to tar again. This experiment does not claim
block-incremental encoding or constant work per edited byte.

## Format and Integration Findings

- Default GNU tar PAX sparse 1.0 output differed across identical-input runs.
  Removing atime/ctime and normalizing extended-header names was insufficient:
  generated member names still included differing `GNUSparseFile.<pid>` values.
  GNU sparse format output was byte-identical for this fixture. This is evidence
  for a deterministic-encoding requirement, not selection of a production format.
- GNU sparse headers are not a complete replacement for CoCalc's original-file
  metadata contract, including subsecond timestamps, xattrs, and hard-link groups.
  Keep that metadata authoritative and test its restoration separately. Do not
  rewrite packed metadata to fake a cache hit while hiding source changes.
- A reusable host-controlled artifact cache must be bounded, evictable, and
  correct after cold starts. Cache identity must refer to the authoritative source
  file/version, not a newly created staging inode. Eviction may cost encoding work
  but must never make backups incomplete or restore depend on the cache.
- Prove a safe way to preserve unchanged-artifact identity through the actual
  immutable backup snapshot. Ordinary files must retain their existing fast path;
  adding sparse encoding must not cause every ordinary file to be rehashed.
- A per-file packed object allows independent restoration, but backup browsing,
  path copies, filename collisions, authenticated format selection, and standalone
  recovery still need integration. Generic tar extraction of user-controlled
  members is not a safe privileged decoder.
- No subvolume snapshot/readonly ioctls, enforced Btrfs project quotas, full
  archive/dearchive RPCs, malicious-input decoding, hard-link groups, xattrs,
  interrupted publication, or production performance tests were run. Native
  snapshot integration and quota enforcement are prerequisites for a canary.

This is worth a next prototype focused on snapshot/cache identity, not immediate
deployment. New encoded backups can use old Rustic readers plus the decoder;
existing unencoded sparse backups still need the separate safe-restore work.
