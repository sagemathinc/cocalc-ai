# CI Audit: September 30, 2026

## Recommendation

Keep the full suite, standard GitHub runners, production builds, and bundle
budgets. Improve lane balance first, then optimize the tests that dominate the
remaining lanes. There is no reason yet to remove database, billing, or
authorization coverage to get a substantial improvement.

The first change uses three server shards, two frontend shards, and a separate
Conat lane. It also stops creating a complete Jest cache for every commit.
Every test-bearing workspace remains selected, and affected-package selection
is unchanged. There are eight test jobs rather than five, each still limited
to four Jest workers. No test was removed or changed.

An initial target is **9-11 minutes for a complete run after the TS7 merge**.
This is an estimate, not a measured result of these changes. Runner variation,
cold caches, and queueing can still put individual runs outside that range.

## Lane Balance

The latest run executed 1,235 frontend suites / 7,183 tests and 640 server
suites. The previous September 9 report measured 972 frontend and 469 server
suites. The suite has grown materially since that optimization work.

Applied the installed Jest 30 sequencer's actual SHA-1 path-based sharding
algorithm to the latest attempt reports:

| Package  | Layout                | Suite counts    | Sum of suite durations per shard |
| -------- | --------------------- | --------------- | -------------------------------- |
| Frontend | current single job    | 1,235           | 1,871 seconds                    |
| Frontend | proposed two shards   | 618 / 617       | 925 / 946 seconds                |
| Server   | current two shards    | 320 / 320       | 1,316 / 1,541 seconds            |
| Server   | proposed three shards | 214 / 213 / 213 | 901 / 968 / 988 seconds          |

Suite-duration sums are worker occupancy, not wall time. They must not be
added to a job's elapsed duration. These figures suggest a reasonably balanced
split without a custom timing-based sequencer or maintained test-file lists.

Conat took 137 seconds of the rest lane's 402 seconds. Moving it to its own
job leaves approximately 265 seconds of serial package testing in rest.
Rest still has about 112 seconds of setup, Python/kernel setup, budget checks,
and post-job work in this sample. It may become the next bottleneck.

The changes add three runner setups, so summed runner time may increase even
as elapsed time decreases. These remain standard Ubuntu runners, which GitHub
documents as free for public repositories; no Blacksmith or larger-runner
subscription is introduced. More simultaneous PRs can still cause queueing.
See [GitHub runner documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

## Cache Policy

At inspection time the API reported 259 active caches using about 9.74 GiB:
10 pnpm caches used 5.36 GiB, 249 Jest caches used 4.36 GiB, and pip used
approximately 22 MiB. This is close to the default 10 GB allowance. Additional
storage or eviction policy depends on repository settings; this audit did not
change billing settings or delete any remote caches.

Previously, every commit created a fresh immutable copy of each lane's entire
Jest cache. The configuration digest was already part of the key, but the
additional commit SHA prevented exact reuse of that baseline.

The revised primary key is stable for a compiler/configuration digest and
lane. It retains OS, Node major, tracked workspace compiler/dependency/config
inputs, and separate lane names. Source changes remain checked by Jest and
ts-jest's own per-file cache keys. A local transformer probe confirmed that
source edits and transform options change those keys and that edited source
emits the edited value.

The tradeoff is explicit: an immutable baseline does not accumulate newly
changed files on every commit. Those files may be retransformed on later runs
until the configuration digest changes. Unchanged baseline files remain warm,
and exact matches no longer create another full cache copy. Track this over
several runs; reconsider the policy if incremental transform costs outweigh
the storage and upload savings.

Fallbacks keep using the same configuration digest and can restore the former
commit-suffixed caches. Newly split frontend lanes can use the old frontend
cache, server-3 can use the old server-2 cache, and Conat can use the old rest
cache. This does not permit reuse across incompatible compiler configurations.
See [GitHub cache matching and immutability](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

The latest main run missed all five Jest cache families after the TS7/config
change. Frontend took 513 seconds there versus 306 seconds in the preceding
main attempt. This is consistent with a substantial cold-cache penalty, but
the comparison also changes revision and runner and is not causal proof.
Do not loosen the global configuration hash merely to label a restore a hit.

## Test Optimization Candidates

### Conat Timer Tests

`conat/core/server.authenticated-caller.test.ts` took 134 seconds, of which
four revocation cases deliberately wait 32 seconds each. A second cluster
revocation file took 43 seconds. These are important real-transport tests,
not disposable tests proving a function was removed.

Follow-up: introduce a narrowly scoped injectable scheduler or controlled clock
for revalidation tests, retaining the production 15-second interval and
10-second failure timeout. Keep real sockets, interests, revoked credentials,
and unavailable-authority assertions. Prove that no refresh happens before a
tick, that refresh happens on a tick, and that disconnect removes interests.
Avoid a global fake clock that also breaks socket/reconnection timers.
Potential Conat package saving: roughly two minutes. Not implemented here.

### Server Module Loading

153 server test files use `jest.resetModules`. Many of the slowest tests already
mock the database: replacing PGlite is not their main opportunity.

| Existing test file                   | Latest suite duration | Tests |
| ------------------------------------ | --------------------- | ----- |
| `projects/create.clone.test.ts`      | 63 seconds            | 30    |
| `conat/api/projects.start.test.ts`   | 48 seconds            | 20    |
| `project-host/control.start.test.ts` | 47 seconds            | 20    |
| `conat/host-status.test.ts`          | 45 seconds            | 14    |
| `conat/api/project-backups.test.ts`  | 37 seconds            | 13    |
| `projects/control/base.test.ts`      | 37 seconds            | 13    |

These suites often reload a broad production import graph per test. First
profile which imports are expensive. Mock unused external/storage/cloud
boundaries explicitly, preferably making unexpected calls fail, while keeping
the tested routing and authorization code real. Reuse a module only where
resetting its state is provably equivalent; do not remove resets wholesale.

Retain real SQL for transactions, uniqueness, migrations, billing balances,
membership allocation, and concurrent/idempotent behavior. Thin RPC routing
and provider orchestration are better mocking candidates than SQL semantics.
The September 9 collaborators improvement already demonstrated this approach.

### Frontend Rendering And Environments

The slowest frontend files were public app (56 seconds), receivables detail
(41), Cloudflare wizard (36), public features (35), docs browser (32), and
public docs (31). Two print-all-documents assertions took 20 and 17 seconds.

Follow-up: keep a representative real-render integration test, use small docs
fixtures for pagination/print/navigation logic, and separate form/business
logic assertions from repeated full Ant Design rendering. Keep accessibility
coverage and full-catalog metadata validation. Do not mock away the behavior
the assertion is intended to exercise.

616 of the executed frontend suites were `.ts` files; only two explicitly
selected the Node environment. Review genuinely pure parser/state tests for
`@jest-environment node`. The extension alone does not prove a test is DOM-free.

The frontend job emitted about 15.2 MB / 73,239 log lines, including 439 act
warnings. Fix the asynchronous test harness and narrow known deprecations;
do not blanket-suppress console errors. Output reduction is a diagnostic and
possible performance benefit, not a quantified speedup yet.

## Flakiness

Across the three downloaded full-run report sets, server retries added about
7-12 seconds per affected shard. Current targeted retries are already useful:
the entire shard is not rerun. Their direct cost is smaller than the module
loading cost, although timeout/cascading failures also waste first-attempt time.

`purchases/statements/email-statement.test.ts` and `create-statements.test.ts`
still hit five-second timeouts, then pass targeted retries. One timed-out setup
continues work and produces a later count mismatch. Make fixtures independent,
finish initialization before assertions, and eliminate clock sleeps with
explicit purchase/statement timestamps. Keep real billing SQL. An increased
timeout alone is not a speed improvement.

## Possible Compromises

| Option                                                    | Potential benefit                                  | Cost / recommendation                                                                            |
| --------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| More standard runner shards                               | Immediate elapsed-time reduction                   | More setup/cache storage and concurrency; implemented conservatively                             |
| Node environment for pure frontend tests                  | Less DOM startup/state                             | Review per file; no coverage reduction needed                                                    |
| Faster test transformer such as SWC                       | Lower cold transform cost                          | Validate mocking, ESM, decorators, and JSX semantics; keep TS7 build checks; separate experiment |
| Move static source-shape checks into checks job           | Removes duplicated AST scans from heavy lanes      | Preserve the checks, wire the local full test command too; modest likely gain                    |
| Smaller UI fixtures with a retained real integration case | Less repeated full rendering                       | Prefer this over deleting functional tests                                                       |
| Full suite only on main/nightly                           | Shorter required PR gate                           | Failures found after merge; not needed initially                                                 |
| Skip production bundle builds on PRs                      | Approximately tens of seconds on current TS7 build | Could miss bundler/assets/budget failures; not worthwhile yet                                    |
| Replace all PGlite tests with mocks                       | Less database initialization                       | Loses SQL/concurrency fidelity and does not fix heavy mock-suite imports; do not do globally     |
| Delete assertion-only tests about removed code            | Reduces maintenance                                | Review individually; cheap tests are rarely a useful wall-time target                            |

## Validation And Rollout

Planner tests check every test-bearing workspace remains covered, exact shard
indices/counts, affected selection, lane uniqueness, and cache fallbacks.
The cache digest tests and all 20 workspace-runner regression tests pass.
Production builds, bundle budgets, four-worker limits, isolated test data,
report artifacts, and targeted retries are unchanged.

Run the complete PR workflow, compare the selected package set and passing test
counts with main, and record the actual critical lane and cache restores.
Then compare at least three main runs with a median and a tail, including cold
and warm runs. Judge the next change against the new bottleneck, not the
September 9 lane weights. The next most attractive follow-up is accelerated
Conat timer coverage and targeted server import profiling.
